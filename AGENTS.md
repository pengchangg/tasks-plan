# Repository Guidelines

GrowJoy (`growjoy`): a family growth-task + points-reward H5 app. One Go binary serves the JSON API, session auth, protected uploads, and a prebuilt React SPA. UI copy, demo data and all of `README.md`/`docs/` are Chinese — write new user-facing strings in Chinese.

## Project Overview

- Purpose: parents define tasks/rewards; children complete tasks, earn points, redeem wishes. Per-family multi-tenant, single process, single replica (one SQLite file + one media dir on one persistent volume).
- Two runtimes, one deployable: Go 1.22 chi service (`cmd/growjoy`, `internal/server`) + React 19/Vite SPA (`src/`) that the same binary serves from `dist/`.
- The served family is never requested by the client: `resolvedFamily` takes the oldest `families` row, so the app is single-family in practice. `POST /auth/child` answers 409 `no_family` when the database has no family.
- Gate list = `make precommit` (`go vet ./...` + `go test -race ./...` + `npm test` + `npm run build`). It runs on every deploy: `make deploy` depends on `make precommit`, so a local deploy cannot ship a red tree — the local pre-commit hook (`.githooks/pre-commit`, `make install-hooks`) runs the same target but only exists on machines that opted in. The two Playwright gates (`check:flow`/`check:ui`) run manually via `make check`, never in the deploy path, and there is no CI at all. No linter or Dockerfile exists (`make fmt` is a plain `gofmt -l -w cmd internal`, not a gate), and the npm/go commands are driven directly; the root `Makefile` wraps them for local use (`make help` lists every target, `make dev` runs the Go server and Vite together) and adds these non-wrapper targets: `make deploy`, `make fmt`, `make logs`, `make stop`, `make clean`, `make distclean`. `make deploy` (precommit gate + cross-compile + rsync + `systemctl --user restart`, documented in `DEPLOY.md`) is the only deploy path, run by hand from the build machine — never two at once, because two rsyncing and restarting one single-replica box would mix `dist/` and binary — and it keeps `bin/growjoy.prev` + `dist.prev` on the host so a failed post-restart readiness/version/entry check restores both. The SPA entry it verifies is parsed out of `dist/index.html`, not guessed from `dist/assets/*.js`. Match surrounding formatting by hand.

## Architecture & Data Flow

```mermaid

  SPA["src/ (React SPA)<br/>useAppStore()"] -->|"fetch /api/v1/*"| API["internal/server<br/>chi router + handlers"]
  API --> DB[("SQLite GROWJOY_DB<br/>WAL, FK, 1 conn")]
  API --> MEDIA["GROWJOY_MEDIA<br/>uploads"]
  API -->|spaHandler| DIST["dist/ GROWJOY_DIST"]
  CLI["cmd/growjoy<br/>serve | admin create-family | seed-demo"] --> API
```

**Backend layout.** Exactly two non-test packages: `cmd/growjoy` (CLI only) → `internal/server` (everything else). There is no `internal/store`, no service/repository layer. `server.go` holds `Config`/`Server`, `Open`/`applyMigrations`, the whole chi router, every write handler, auth, uploads and the DTOs; `state.go` holds the `/state` read side (`ensureInstances`, `weekStart`, `streaks`, `state`/`getState`); `stats.go` holds `GET /stats` end to end (`statsWindow`, `scheduledTaskCount`, the `stats` handler); `admin.go` holds non-HTTP operations (`CreateFamily`, `SeedDemo`, `EnsureDemo`); `games.go` holds the Klotski resource (the 5 built-in layouts and their sequential unlock rule, `getKlotski`/`completeKlotski`, and `klotskiShortest` — an in-process BFS that computes each level's moves floor once; `getKlotski` ships that same floor per level as `minMoves`, so the UI labels 最少 N 步 and cross-checks the client hint against the number the complete endpoint enforces); `quizzes.go` holds the quiz-game resource (口算闯关 `timed_calc` + 找规律 `pattern_quiz`: the `quizGames` spec table — name, score→point divisor, score ceiling — `getQuizzes` (today/all-time best, today's plays and the last 20 rounds per child) and `submitQuizScore`, which writes one `game_history` row per round and credits that round's FULL score (`awarded = score ÷ the spec's unit`, so every round pays even when it is not a record; `game_scores` keeps the day's best only for display; the ledger `reference_id` carries the round's history id, so each round is one ledger row) — it REQUIRES an `Idempotency-Key` because a re-sent round would otherwise pay twice); `homework.go` holds the homework resource (DTOs, the day read, the parent-side multipart writes, the fixed subject list and the image normalisation: EXIF orientation → longest edge 2560 → JPEG q85); `ratelimit.go` holds the token buckets, the argon2 slot gate, `recoverPanic` and the error helpers; `migrations/*.sql` is `//go:embed`-ed. Split by resource, not one file per handler: a new read-only surface belongs with its siblings (`state.go`/`stats.go`), a new resource gets its own file like `homework.go`.

**Middleware chain.** `requestLog` (security headers `nosniff`/`DENY`/`same-origin`, then one access line) wraps `recoverPanic` (a handler panic becomes a logged 500, and a response already written is not rewritten) wraps the mux. `/health/live`, `/health/ready` sit outside the API; `r.Route("/api/v1", ...)` applies `sameOrigin`; the public auth routes add `s.authLimit`; a nested group applies `authenticate`; role gating is `s.parentOnly(h)` or an inline actor check. No timeout middleware, no CSRF token, no CORS headers, no `Cache-Control`: CSRF rests on `sameOrigin` (GET/HEAD/OPTIONS pass; `Sec-Fetch-Site: cross-site` → 403 `cross_site_request`; a non-empty `Origin` whose host != `r.Host` → 403 `origin_mismatch`) plus `SameSite=Lax`. The check compares `Origin` with `r.Host`, so any proxy in front MUST preserve the browser's `Host` — this is why the Vite dev proxy sets `changeOrigin: false`.

`submit`/`redeem` reject a parent actor (`403 forbidden "child access required"`) and `review` is registered `parentOnly`, so a session can never do both. `PATCH /redemptions/{id}` copies the same three actor guards inline (there is no `childOnly` middleware) and is `multipart/form-data` (field `completed`, optional `note` + `files`, same sniffing/limits as submit): it writes `completed_at`/`completed_note` plus `attachments.redemption_id` as **one** completion record, and `completed=false` clears all three (rows deleted, files removed after commit). It deliberately takes **no** `Idempotency-Key`: no ledger row and no `children` column is touched, and a replay only re-creates evidence rows. The three create routes are subrouter `/` routes: `src/store.ts` always emits the trailing-slash form.

**Data flow.** The SPA never loads resources individually: `GET /api/v1/state` returns the whole `State` aggregate (role, active child, children, tasks, submissions+attachments, wishes, ledger, redemptions, family `timezone`) and `/stats` a separate payload. Mutations return `{"id":"..."}` (200) or 204, and `src/store.ts` re-fetches both, and its `childTasks` memo (which every task list and its counters read) hides instances that are `completed` **and** dated before the family's today — the task lists are "what to do now", past completions belong to the growth calendar, while `todo`/`pending_review`/`rejected` instances from any day stay visible for the parent who still has to confirm them. No optimistic updates — the server is the source of truth. `State.timezone` is the family's IANA zone (`loc.String()` from `familyLocation`), which the child growth calendar MUST use to turn UTC instants into family-local `YYYY-MM-DD` — a device-local date would disagree with `due_date` and `/stats` near midnight.

**Reads write.** `state()` calls `ensureInstances(ctx, family)`, which materializes `task_instances` for today (`daily`), the current ISO Monday week (`weekly`, `due_date` = Monday + `(repeat_weekday+6)%7` days, `period_key` = Monday) or the creation date (`once`, `period_key = "once"`) with `INSERT OR IGNORE` + `UNIQUE(template_id, period_key)`. Day/week buckets use the family's IANA timezone (`Asia/Shanghai` default). `state()` output order is a UI contract: children/ledger/redemptions/submissions ascending, tasks and wishes `created_at DESC`, every slice normalized to a non-nil array.

**Invariants to preserve (all enforced in SQL, never in app locks).**
- Every statement carries `family_id` from the session row; `RowsAffected() == 0` → 404. A query missing `AND family_id = ?` is a cross-family leak. Child-scoped reads use the literal `AND (? = 'parent' OR child_id = ?)` bound to the actor type + selected child.
- Exactly-once effects: `point_ledger UNIQUE(family_id, reference_type, reference_id)` + `INSERT OR IGNORE` with a `RowsAffected()==1` guard before crediting growth, status-guarded `UPDATE ... WHERE status IN ('todo','rejected')` (`changed != 1` → 409 `conflict`), `reviewTask`'s two status asserts (submission `UPDATE ... WHERE reviewed_at IS NULL`, instance `UPDATE ... WHERE status='pending_review'`, each with its own `RowsAffected()!=1` → 409 `conflict`) so a second review can never re-credit, `task_instances UNIQUE(template_id, period_key)` (a multi-weekday `weekly` template gets one instance per weekday with `period_key` = `<周一>:<星期>`, while an empty `repeat_weekdays` — every row written before 007 — keeps the bare `<周一>`, so `ensureInstances` must keep producing exactly that key for legacy rows; `scheduledTaskCount` reads the same set), `homework_done PRIMARY KEY(homework_id, date, child_id)` (one tick per subject-day **per child**, 009) with homework ledger keys `<homework>:<date>:<child>` / `<date>:<child>` so two siblings ticking the same holiday day each earn their own points and the day bonus is per child, `game_scores PRIMARY KEY(family_id, child_id, game, date)` + quiz ledger key `<game>:round:<historyID>` (one daily-best row per child per game, kept only for display; each round pays its own score and its own ledger row), `INSERT OR IGNORE` keys, and `idempotency_keys PRIMARY KEY(family_id, actor_id, operation, key)`.
- `POST /tasks/{id}/submit`, `/review`, `/wishes/{id}/redeem`, `children/{id}/points` and `games/quizzes/{game}/score` REQUIRE an `Idempotency-Key` header (else 400 `idempotency_required`); a replay returns the stored status with `{"replayed": true}` and MUST NOT repeat side effects. `claimIdempotencyKey` takes the key as the transaction's FIRST write (`INSERT ... ON CONFLICT DO NOTHING`, sentinel `status_code = -1`), so a concurrent same-key request cannot run the effects twice: the loser's INSERT conflicts, its transaction rolls back, and it answers the stored status. A loser that finds the sentinel (or no row, because the winner rolled back) gets 409 `conflict` instead. `submit` reads the instance state only after the claim, so a same-key retry replays the stored 200 rather than tripping over the status the first attempt already moved. `status_code` is the only column ever read back (`response_body` is write-only).
- `streaks` reads at most `streakLookbackDays` (400) of ledger history per child — the window, not the whole life of the family, is what `/state` pays for on every request. `children.experience` is a `REAL` column scanned into a `float64` and floored to `int` before `% 100`/`level`, so one fractional value cannot break `/state` with a scan error. `verifySecret` rejects a stored argon2 hash whose cost parameters fall outside 8 MiB·1 iteration…256 MiB·10 iterations, because those parameters come from the row, not from the process.
- The pool is `SetMaxOpenConns(1)`: close each `*sql.Rows` before the next query. Pragmas (`WAL`, `foreign_keys=ON`, `busy_timeout=5000`) are applied once at `Open` on that single connection, so raising the limit silently drops all three — `deleteChild`'s `ON DELETE CASCADE` depends on `foreign_keys`.
- Internal failures NEVER reach the client: use `s.internalError(w, r, err)` (or `s.uploadError`, which keeps the `upload_failed` code) — it logs method/path/error via `s.log` and answers `{"error":{"code":"internal","message":"internal server error"}}`. Never pass `err.Error()` to `problem(...)`. `/health/ready` likewise answers a bare "database unavailable".
- Auth is throttled on two independent budgets (`ratelimit.go`'s const block): `authIP` (60 burst / 1 per second per client address, applied by `s.authLimit`) protects the process; `authFailures` (10 burst / 1 per 30 s per family actor) protects the parent password, the app's only credential. The failure budget is charged ONLY after a wrong password (check → charge → 401), so the family is never locked out of its own parent end — do not move that check before verification. `clientAddr` deliberately ignores `X-Forwarded-For`; buckets are evicted only by `Sweep` (idle > 30 min).
- The child end is the default: `POST /auth/child` opens (or reuses) a child session, demoting a parent session by deleting its row; `POST /auth/parent` verifies the submitted password against each of the family's parents in `created_at,id` order and binds the session to the match; `PATCH /session/child` switches profile for both actor types and, for a child session, rewrites `actor_id=selected_child_id`. A child session mirrors its profile in `actor_id`, so the scoping form and the per-child idempotency keys stay exact. Parent authority is per visit: a reload starts the child end again and the password gate is client-side state (`Shell`'s `parentGate`) backed by a 12 h parent session (child sessions last 30 d).
- Every argon2 call goes through `s.hashPassword` / `s.verifyPassword`, which serialize on a 4-slot gate (`argon2Slots`) because each call allocates 64 MiB. Direct calls to `hashSecret`/`verifySecret` bypass that bound.
- Points are double-bookkept: ledger is truth; `children.experience` is **total** experience, the API exposes `experience % 100` and `level = 1 + total/100`, approval adds `max(points/5, 1)` and recomputes the level from the new total. `children.points_balance` may go **negative**: un-checking a homework deducts the points it earned even if the child already spent them (the ledger row remembers which child earned it, so a sibling's untick cannot take the other child's points) (006 rebuilt `children` to drop the old `CHECK(points_balance>=0)`; SQLite cannot alter a CHECK, and the rebuild only works because `runMigration` turns `PRAGMA foreign_keys` OFF on the pool's single connection before the transaction and back ON after it — the seven tables keep `ON DELETE CASCADE` clauses pointing at `children`, so with FKs on the rebuild's `DROP TABLE children` really empties them (that is how the deployed family lost every task, submission and ledger row on 2026-11-05). `PRAGMA defer_foreign_keys=ON` does NOT prevent that; never restore it.) A wish redemption still refuses (`409 insufficient_points`) unless `points_balance>=points_cost`, so a negative balance can never be redeemed against.

**Frontend shape.** `main.tsx` → `App` → `BrowserRouter` with a catch-all route rendering `Shell`. `Shell` calls `useAppStore()` **once** and passes the whole store object down as a `store` prop; it picks child vs parent shell from `location.pathname.startsWith("/parent")` plus `state.role`, and gates on `ready`/`connected` plus a `parentGate` password modal (a `/parent` deep link is stashed and restored after unlocking). While the parent end is unlocked the account menu (`.role-menu`, visible at every width, unlike `.sidebar-bottom`) also grows a 修改家长密码 entry that renders `ParentPasswordModal` — a `TaskForm`-shaped `.form-modal`, deliberately not `.pin-modal`, whose wrong-current-password branch is a 401 the store MUST NOT replay; that is why the route sits under `/auth/`. Route tables: `ChildLayout` (`/child`, `/child/tasks`, `/child/homework`, `/child/wishes`, `/child/ledger`, `/child/growth`, `/child/games`, `/child/games/klotski` (`?level=`), `/child/games/calc`, `/child/games/pattern`, `*` → `/child`) and `ParentLayout` (`/parent`, `/parent/children`, `/parent/tasks`, `/parent/wishes`, `/parent/homework`, `/parent/games`, `/parent/stats`, `*` → `/parent`). The child bottom nav therefore has five tabs, which is why `.bottom-nav a{min-width}` is 58px (积分明细 is not a sixth tab — it is reached from the balance card). `src/features/ledger.tsx`'s `ChildLedger` renders `/child/ledger` from `state.ledger` alone (no new endpoint): the child's own rows newest-first under family-local `.ledger-day` heads, a `.ledger-total` header (balance + `共 N 笔记录`), rows reusing the parent overview's `.activity-list`, and each row's `.ledger-after` 结余 comes from `balancesAfter` — walk the newest-first list subtracting each amount from the current `pointsBalance`, so the newest row's 结余 is the balance by construction. The 我的积分 card's 积分明细 link (`.balance-link`) is that screen's only entry. Level-ups are the second reward channel: `Shell` keeps a per-child level baseline with the same base-on-first-state semantics as the reward queue (and ignores the parent end), so a `level` increase answers exactly once on the child end as a `LevelUpToast` (`.level-up`, `pointer-events:none`, auto-dismiss 3.6 s, no close button — deliberately not `.reward-celebration`, which is a click-through queue). `WishCard` prints `.wish-progress` (bar + `已攒 N/C 积分` aria-label, both clamped to 0..cost so a negative balance cannot draw a negative bar) and swaps 去兑换 for a disabled `还差 N` button when the child cannot pay yet; `WishMini` swaps 继续努力 for `还差 N`. `/child/growth`'s achievement card also renders a `.badge-row` of six `.badge-chip`s (3/7/14/30/60/100 consecutive days, `locked` below the threshold) and its copy names the next badge in `再坚持 N 天` terms. `ChildHome` itself leads with the homework module: `TodayHomework` (今日作业 heading + 按日期查看 link + the daily proverb banner + that day's cards or the empty state) sits directly under the greeting, above the growth-partner hero. It always shows the family-local today — arriving from `/child/homework` after browsing another date re-loads today instead of showing the stale day — and its cards plus the full-screen lightbox are the same `HomeworkDay` component the dated screen renders, so the two surfaces cannot drift apart. Both child surfaces pass `HomeworkDay` an `onDone`, which renders the per-card 完成 checkbox (`.homework-check`, `.homework-card.done`); `Homework.done` is the flag for **the day on screen**, not for the whole entry, so a holiday-range homework can be ticked day by day — the store's `toggleHomeworkDone` flips the row locally first (a reload would snap the controlled box back while the request is in flight) and `POST /homework/{id}/done` is idempotent on the done row (`INSERT OR IGNORE` / `DELETE` plus a `RowsAffected()==1` gate), so it takes no `Idempotency-Key`; the two ledger entries it writes are keyed per child (`reference_type` `homework` with `reference_id` `<id>:<date>:<child>`, and `homework_bonus` with `reference_id` `<date>:<child>`), and `homework_done` carries `child_id` itself (009), so two siblings ticking the same holiday day each earn their own 5 points instead of sharing one row; only a real state flip credits 5 points per subject (+5 once *that child* has every subject of the day done) and un-checking deletes those rows and claws back exactly what that child earned (the balance may end up negative; a redemption still needs full funds). The checkbox is `disabled` while its own POST is in flight, and a failed tick rolls the optimistic flip back because `refresh()` only re-reads `/state` — the credit surfaces through the normal `RewardCelebration` ledger queue **and** as an in-card `+N` pill (`.homework-award`): `run` returns the operation's value, so `toggleHomeworkDone` hands the response's `awarded` back to `HomeworkDay`, which owns the pill in local state for 2 s (`aria-hidden` — the banner already announces it) and never guesses the number client-side; un-checking clears the pill and the reversal surfaces through a `已取消完成，扣回 5 积分` toast. The parent end renders the same items without that checkbox. The child `TaskCard` collects nothing: 完成任务 / 重新提交 post `POST /tasks/{id}/submit` on the spot (one tap → `pending_review`), guarded by a local `busy` flag on the button — there is no submit panel, no `note`, no file picker, and a mis-tap can only be undone by the parent's 退回 (no un-submit endpoint for `todo`). Submitted evidence is rendered by one shared `SubmissionEvidence` (fed by `store.latestSubmissions`, the newest submission per task for the child on screen) in both the child `TaskCard` and the parent `AdminTaskRow`: images become `.media-thumb` thumbnails that open a `.media-viewer` overlay, videos become inline `.media-video` players, and any attachment without a `url` (local `File` entries before upload, `data.ts`/vitest seeds, a file the browser cannot decode) falls back to the plain `.attachment-chip` label. Because a task submission now carries no note and no media, a submission with **neither** renders only its `.evidence-heading` line (我提交的内容 + the family-local submitted time) — the `未填写文字备注`/`未添加照片或视频` placeholders are gone; note and media still render for demo-seeded and legacy rows. Redemptions are rendered by one shared `StarWishList`/`StarRow` on both ends: the child `/child/wishes` screen feeds it `store.childRedemptions` (its own rows, newest first) and `/parent/wishes` feeds it the reversed `state.redemptions` with `ownerName` — read-only, no `onToggle`. Only the child row gets the 标记完成 panel (`note` + `image/*`/`video/*` pickers — the only place in the app that still collects evidence for a write; the textarea is capped at 30 runes like the server, `确认完成` disables itself while the PATCH is in flight and the panel closes only after it succeeds, and a repeat 确认完成 replaces that redemption's attachments instead of appending to them) and the 撤销完成 confirm; a `completedNote`/`attachments` pair is rendered under the line by `MediaGallery`, and the row's dimming is applied to the line only (`.star-done>.star-line`) so the confirm modal is never trapped in the row's stacking context — and `.star-done>.star-evidence` is deliberately **not** dimmed for the same reason: `opacity` would create a stacking context around the block the `.media-viewer` is opened from, and the `position:fixed` overlay would then paint under the 68px sticky `.topbar` (`z-index:30`), leaving 关闭预览 unclickable. The topbar carries a 刷新 icon button (`.refresh-button`, aria-label/title 刷新) on both ends: `store.actions.refresh()` re-fetches `/state` + `/stats` and re-loads the homework date on screen inside `run`, shows a 「已刷新」 notice, and removes it 2 s later only if it is still that exact message (so a failure that replaced it is never wiped); `check:flow` asserts one click re-fetches `/state`, paints the 已刷新 toast (found by `role="status"` + text, not by a class) and that the toast is gone again within 2 s. The parent overview's 奖励积分 button opens `PointsForm` (`增加积分`/`扣除积分` toggle, integral `积分数量` 1–500 with 5/10/20/50 presets, optional 30-rune `原因`, 「确认奖励」/「确认扣除」), which posts that signed amount through `store.actions.awardPoints` — the same ledger as task approval, except a deduction only lowers the balance. Both viewers (the evidence `.media-viewer` and the homework viewer) are CSS overlays only — they deliberately do NOT call the browser Fullscreen API, which in the Android WebView rotated the screen on every tap; their `<video>`s carry `playsInline` for the same reason. Both embed the same `ZoomableImage` (pinch, double-click, wheel and `放大`/`缩小`/`重置` buttons in `.zoom-controls`, current zoom mirrored to `data-scale`): a zoomed image pans, and the homework swipe handler checks that scale so a swipe released while zoomed pans instead of changing the image.

**Both ends share one screen, so nothing there is static.** `useAppStore` re-runs `pull(true)` every `autoRefreshMs` (60 s) and only while `document.visibilityState === "visible"`; `keepRole` exists because `request()` re-opens the child end when a parent session has expired, and a poll nobody is watching must not throw the parent off the page (a half-filled form would vanish with it). `ParentLayout`'s 任务管理 link grows a `.nav-badge` with the `pending_review` count, and `ParentOverview`'s 需要你的确认 header grows a 全部确认 button (only when more than one) behind a ConfirmModal (确认全部) that calls `store.actions.reviewAll(ids)` — deliberately **sequential** `POST /tasks/{id}/review` calls, each with its own `Idempotency-Key`, each swallowing its own error into a skipped count, because a batch endpoint would need a new ledger/idempotency story for something a parent taps once a week. Rejecting is now a two-step `.review-actions.rejecting` row (`input.review-note`, 30 runes, 确认退回 disabled while blank) — a 退回 with no reason was the least actionable thing in the app — and the stored reason prints back on the child's card as `.review-note-line` (`家长：…`). Two more form affordances, both frontend-only: `TaskForm` create mode renders `taskPresets` (`.preset-list` → `.preset-chip`, 3 categories × 5 items, `title` carries the description) that only pre-fills fields and never creates, and a `weekly` task picks several weekdays (`.weekday-chip` × 7 plus `.weekday-quick` 工作日/周末/全选, submit disabled when none is checked), with `repeatWeekday` demoted to “the first checked day”.

**Family-local dates only.** `ChildHome`'s greeting, `TaskCard`'s due label, `StarRow`'s redemption date, `DayTaskRow`'s 原定 badge, the ledger/submission timestamps and `TaskForm`'s default weekday all go through the helpers next to `dateText` (`familyToday`/`familyDate`/`weekdayOf`/`weekdayIndex`/`monthDayText`), which read the family's IANA zone. A device-local `new Date().toISOString().slice(0,10)` loses the last 8 hours of a Shanghai day and disagrees with `due_date` and `/stats`. Any component that needs today takes a `today`/`timezone` prop instead of reading the clock itself (`TaskCard`, `DayTaskRow`, `StarWishList`/`StarRow`, `TaskForm`); adding one more `new Date()` to a render is the bug this list exists to prevent.

**Server-side analytics.** `GET /stats` is computed for `x.SelectedChildID` only — it is not a family aggregate — over the window `?from`/`?to` name (inclusive family-local `2006-01-02` dates; `statsWindow` defaults to the trailing 7 days and answers 400 `invalid_request` for one end only, `from > to`, an unparseable date or a span over `statsMaxRangeDays` (92)). `totalTasks` is **derived from the templates** (`scheduledTaskCount`: `daily` once per day from its creation day clamped to the window, `weekly` only on its `repeat_weekday`, `once` on its creation day, `active=1` templates only) because `ensureInstances` materializes only the day or week that was read, so an instance-based count is 0 in every historical window. `completedTasks` counts the `approved=1` submissions reviewed inside the window, the ledger sums use the same window, `daily` carries one bucket per day — `周日..周六` when the span is ≤ 14 days, else `M/D` — and `categories` is derived from those confirmations (count descending, then name) so a family's own category names survive. The payload echoes `from`/`to`. The child `Growth` screen does NOT consume it. It renders a **growth calendar** derived entirely from `State`: `familyDate`/`dayDigest`/`dayActivity` (`src/domain.ts`) bucket `tasks` by `dueDate` and submissions/ledger entries by their family-local date, so a day shows its scheduled instances with status plus a 「补录记录」 group for tasks whose newest submission lands on another day than the instance's `due_date` (exactly one day per task — the newest submission wins, matching the server's `submitted_at` order); the calendar dots are `backfill` if that day received a backfill, else `done` when every scheduled instance is completed, else `open`. Every cell also prints its 农历 day (a 节日 name replaces it) and, in the corner, a 「休」/「班」 mark from `State.holidays` + `State.makeupWorkdays` — weekends count as 休 unless the table lists them as 调休上班日 (`src/lunar.ts`); the same `LunarTag` sits under the day-panel heading, the child home greeting and the homework date bars. `ParentStats` is its only consumer, and it requests its own window through `store.actions.loadStats` instead of reading the default snapshot in `store.stats`; its effect keys on `activeChild.id` + the range (not the whole `store.state`), so the 60 s poll does not re-ask for the same window. The parent `completedTasks`/ledger reads are bounded in SQL (`reviewed_at`/`created_at` between the window's UTC bounds), so an old family does not pay for its whole history on every `/stats`.

## Code Conventions & Common Patterns

### Go

- Handlers are methods registered directly in `Handler()`: `func (s *Server) verbNoun(w http.ResponseWriter, r *http.Request)`. Files are split by concern, not one file per handler.
- Dual-purpose save handlers: `chi.URLParam(r, "id") == ""` means create, otherwise update (`saveChild`, `saveTask`, `saveWish`).
- JSON out: `writeJSON(w, status, v)`; errors ALWAYS via `problem(w, status, code, message)` → `{"error":{"code":"...","message":"..."}}` with snake_case codes — in use: `invalid_request`, `invalid_credentials`, `unauthorized`, `forbidden`, `not_found`, `invalid_state`, `too_many_requests`, `idempotency_required`, `upload_too_large`, `unsupported_media`, `too_many_files`, `insufficient_points`, `insufficient_balance`, `wish_unavailable`, `last_child`, `conflict`, `internal`, `upload_failed`, `unavailable`, `no_family`, `origin_mismatch`, `cross_site_request` — and internal ones through `s.internalError`/`s.uploadError`, never with the raw error text.
- JSON in: `decode(r, v)` — 1 MiB `io.LimitReader` **and** `DisallowUnknownFields()`; a client field absent from the Go input struct is a hard 400. Multipart submit and redemption completion read `r.FormValue("note")` instead, capped at 30 runes.
- Raw inline SQL with `?` placeholders. No ORM, no repository layer, no prepared statements. Scan into the exported DTOs (`Child`, `Task`, `Submission`, `Wish`, `Ledger`, `Redemption`, `State`) — camelCase `json` tags over snake_case columns; request bodies use unexported per-resource types (`childInput`, `taskInput`, `wishInput`) or inline anonymous structs.
- Multi-write flows use `tx, err := s.db.BeginTx(ctx, nil)` + `defer tx.Rollback()` + explicit `Commit()` — the exact set is `CreateFamily`, `SeedDemo`, `deleteChild`, `deleteTask`, `submitTask`, `reviewTask`, `redeemWish`, `completeRedemption`, `awardPoints`, `saveHomework`, `deleteHomework`, `setHomeworkDone` (done row + ledger + balance). Never touch `s.db` after `Commit()` in the same handler.
- Time: read `s.now()` — NEVER `time.Now()` in a handler, and never the process-local zone for day/week math (`familyLocation(ctx, family)` instead). Persisted instants are `nowText(t)` = UTC `RFC3339Nano`; date-only values (`due_date`, `period_key`) are family-local `2006-01-02`. Note `RFC3339Nano` trims trailing zeros, so lexicographic ordering within the same second is unreliable.
- IDs: `id(prefix)` = `prefix + "_" + 16 random bytes hex`. Prefixes in use: `fam par child ses tpl task sub att media wish red led`. No UUIDs in Go (`google/uuid` is indirect and unused).
- Auth: argon2id PHC hashes (`hashSecret`/`verifySecret`, cost re-parsed from the stored string) reached through the gated `s.hashPassword`/`s.verifyPassword`; sessions persist only `tokenHash(raw)` = sha256 hex; cookie `growjoy_session` (`Path=/`, `HttpOnly`, `SameSite=Lax`, `Secure=GROWJOY_SECURE_COOKIES`, `Expires`, no `Max-Age`/`Domain`), 30 d for the child end and 12 h for a parent session (which a reload replaces anyway). `CreateFamily` requires a code/name/username and `validPin(password)` — exactly four decimal digits (`server.go`) — and validates the IANA timezone. `validPin` is enforced at the two places that *set* a credential (`CreateFamily`, `POST /auth/parent/password`); sign-in never checks the format, so a family whose row predates the rule keeps unlocking with its long password until it changes it. Changing the password requires the current one, charges the same `authFailureKey(code, "parent")` budget as `/auth/parent` (a correct password never charges it), rewrites **every** `parents` row of the family — `UPDATE parents SET password_hash=? WHERE family_id=?`, since `parentSecrets` gives each row a chance to match — and deliberately leaves `sessions` alone, so the parent that changed it stays in the parent end. That route lives under `/auth/` on purpose: `src/store.ts` replays any 401 outside `/auth/` after re-opening the child end, which would demote the parent session on a typo. No session GC on the request path — `s.Sweep(ctx)` deletes expired sessions and idempotency keys older than `idempotencyRetention` (30 d), evicts idle limiter buckets, is called on boot and hourly by `serve`.
- Credential budgets are keyed per family via `authFailureKey(code, "parent")` (`UPPER(TRIM(code)) + ":parent"`), where the code comes from the resolved row, so client input cannot mint unbounded buckets. Only the parent password is a credential, so only `/auth/parent` and `/auth/parent/password` charge it — both through the same `authFailureKey(code, "parent")` bucket, so the two entries cannot double an attacker's attempts.
- Uploads (`submitTask`, `completeRedemption` and `saveHomework`): homework caps at `homeworkMaxUpload` (100 MiB) through `http.MaxBytesReader` + `ParseMultipartForm()` and is limited to 6 files; the other two use `http.MaxBytesReader` 101 MiB, `ParseMultipartForm(100 MiB)`, `defer RemoveAll()`, field `files`, ≤6 files, ≤100 MiB total, and the `note` field is capped at 30 runes (the same budget as a manual points note). `submitTask` in `src/store.ts` still posts a `FormData` carrying an empty `note` and **no** files: the child end's one-tap submit collects nothing, and dropping the multipart body entirely would be a 413 `upload_too_large`, not a valid empty submission. `inspectUpload` sniffs 512 bytes plus MP4 (`ftyp` + brand) / WebM (EBML + `webm`) probes; allow-list jpeg/png/webp ≤10 MiB, mp4/webm ≤100 MiB. A non-multipart body is reported as 413 `upload_too_large`, not 415. Files land in `MediaDir` as `media_<hex><ext>` with `O_CREATE|O_EXCL|O_WRONLY, 0600`, written **before** the transaction, with a cleanup closure that removes written files if a later step fails (never after a successful commit) — and that also drops the copies a replayed claim just wrote. Serving is session-authenticated and family-scoped, `filepath.Base` guards traversal, `http.ServeContent` handles ranges. An `attachments` row belongs to exactly one of `submission_id` / `redemption_id` (CHECK over both, both columns nullable); `mediaForChild` unions both owners so deleting a child also removes their redemption evidence.
- Migrations: `001_init.sql` re-runs on EVERY boot outside any transaction and therefore MUST stay idempotent (`IF NOT EXISTS` / `INSERT OR IGNORE`; it self-inserts `schema_migrations` version 1, which `applyMigrations` skips recording); versions > 1 run once inside a transaction. Never edit an already-applied file — add the next `NNN_*.sql` numbered ≥ 2 (a re-run of an `ALTER TABLE ADD COLUMN` would fail; `001` is the whole schema because nothing was deployed when it was flattened). Filenames must be `NNN_name.sql` with an integer prefix parseable by `strconv.Atoi`.
- `saveTask` create returns a **task instance id** (looked up as the newest `task_instances` row of that template), and every later task route addresses an instance, not a template; the template is reached through a subquery. Updating a task only syncs the instance while it is `todo`/`rejected` and unsubmitted.
- `deleteWish` is a soft delete (`deleted_at` + `is_active=0`); `wishInput.IsActive` is a `*bool` written as `is_active=COALESCE(?,is_active)`, so a `PUT` that omits it keeps the current flag instead of silently delisting the wish; `deleteTask` sets `active=0` and deletes that template's instances; `deleteChild` reads the child count and the media list inside the transaction (409 `last_child`), re-points and deletes sessions, then best-effort removes the child's media files after commit; `mediaForChild`/`mediaForTemplate` take a `queryer` so they can run on `tx` (the pool holds one connection, so `s.db` inside a transaction deadlocks).
- `spaHandler` returns `index.html` with 200 for any unknown path, so a broken asset reference fails silently instead of 404ing. `/favicon.ico`, `/favicon.svg` and `/apple-touch-icon.png` are real files in `public/` (see the committed artifacts list) and are served from `dist/` like any other asset; `index.html` links all three.

### TypeScript / React

- `src/App.tsx` keeps the shell, the two route tables and the task/wish/growth screens (`App`, `AppErrorBoundary`, `Shell`, `ParentPinModal`, `ParentPasswordModal`, `RewardCelebration`, `LevelUpToast`, `ChildLayout`, `ChildHome`, `TaskCard`, `ChildTasks`, `ChildWishes`, `StarWishList`, `StarRow`, `Growth`, `CalendarGrid`, `DayTaskRow`, `ParentLayout`, `ParentOverview`, `ParentChildren`, `ParentTasks`, `AdminTaskRow`, `SubmissionEvidence`, `MediaGallery`, the `*Form` modals). Do not keep growing `App.tsx`: new feature code starts in `src/features/`, and `ui.tsx` is the only place to add a primitive more than one feature needs (importing `App.tsx` back from a feature would be a cycle).
- All application state lives in `useAppStore()` (`src/store.ts`) and is passed down as a `store` prop. No context, no Redux/Zustand, no per-page fetching, no `localStorage` — that is why the parent gate cannot survive a reload. Add queries as `actions` entries on the returned object and mutate through `run(() => ...)`, which clears the message, runs the op, then refreshes server state and **returns the operation's value** (`undefined` when it failed) so a caller can react to what the server actually did — that is how the homework card learns its `awarded` — `loadStats(from, to)` is the one action outside `run`, because the stats screen keeps its own payload and keeps the previous numbers when the request fails, while `store.stats` stays the default 7-day snapshot the parent overview reads. Homework is the second slice outside `/state`: `store.homework` holds `{date, items, holiday?}` for the day on screen (plus `store.today`, the family-local today both homework screens default to), `setHomeworkDate` loads it through the module-private `loadHomework`, and the three mutations (`saveHomework`, `deleteHomework`, `deleteHomeworkMedia`) run through `run` and then re-load that date themselves **and set their own success message inside the operation** — `run`'s own message handling would otherwise blank or overwrite it. Quizzes are the third slice outside `/state`: `store.quizzes` holds the `GET /games/quizzes` report, refreshed by the child/parent games screens (`loadQuizzes`) and after every `submitQuizScore` (which runs through `run` and returns the response's `awarded`, so the 再闯一次 overlay prints the number the server actually paid).
- Requests go through the module-private `request()` helper hitting `/api/v1${path}` (`credentials: "same-origin"`; `Content-Type: application/json` for every non-`FormData` body, including DELETE). Write helpers come from `json(method, value, idempotent)` — pass `idempotent = true` for submit/review/redeem (it attaches a module-private `idempotencyKey()` as `Idempotency-Key`; `submitTask` hand-builds `FormData` and sets its own key). `idempotencyKey()` prefers `crypto.randomUUID()` but that method exists only in a secure context, so a plain-HTTP LAN deployment (where `isSecureContext` is false) falls back to a v4 UUID built from `crypto.getRandomValues`; never call `crypto.randomUUID()` directly on a request path or every idempotent write throws before `fetch`. `request()` re-opens the child end and replays the original call once when a non-auth route answers 401 — the same idempotency key, so the retry is safe. A new write path that bypasses `json(..., true)` turns that retry into a double mutation.

Write request bodies MUST be typed with `ChildInput`/`TaskInput`/`WishInput` from this file: they mirror the Go `childInput`/`taskInput`/`wishInput` field sets, and `decode()` runs `DisallowUnknownFields()`, so spreading a server DTO (with its `id`/`dueDate`/`status`) back into a request is a 400. `AppState.timezone` is required; `AppState` also carries `holidays` (`HolidaySpan[]`, the official 放假 ranges) and `makeupWorkdays` (`string[]`, 调休上班日), so every literal `AppState` — `src/data.ts`'s seed and `src/domain.test.ts`'s fixture included — must set all three (the growth calendar cannot bucket days without the zone, and cannot mark 休/班 without the table).
